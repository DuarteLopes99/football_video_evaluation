# Changes 2026-11-13: repository layout, GPU automatically, Windows, pinned packages

The processing works much better after the v0.4 changes (replay palette, PTZ camera units, ball tracker, attacks
near goal). This round consolidates the repository and makes a GPU computer process a match faster with no setup.

## 1 · Repository: two projects, one dashboard

| Decision | Why |
|---|---|
| `football_video_evaluation/` holds two independent projects: `global_video_analysis/` (full match) and `offside_code/` (offside on one frame) | different inputs (a whole recording vs a few frames), different speed needs, different tests; neither imports the other |
| One shared `.venv` and one launcher (`start.command`, now also `start.bat` for Windows) | one install, one dashboard: tabs *Analyse · Manual decisions · Match screen · Results & opportunities* (global) and *Offside* (offside_code mounted under `/off/`) |
| `global_video_analysis/start.command` kept as a forwarder | old Desktop shortcuts keep working |
| Models (`*.onnx`, `*.pt`), videos, raw data and run outputs stay out of git | downloaded by `scripts/get_models.py` / `offside_code/scripts/download_models.py`; recordings live in the video libraries (`docs/VIDEO_STORAGE.md`) |
| `offside_code` tests run under pytest | each synthetic check has a `test_*` entry point; the checks that take arguments are called `check_*` (pytest took their arguments for fixtures) |

## 2 · GPU used automatically (`football_eval/accel.py`)

The detector is ~95 % of the processing time (analysed frames × tiles per frame), so it is where a GPU pays.

* **YOLOX through onnxruntime** (`detection.runtime: auto`, default): every GPU execution provider of the installed
  onnxruntime is tried (CUDA, ROCm / MIGraphX, DirectML, CoreML, OpenVINO), each is benchmarked on a 640-px tile
  against the CPU and the fastest is kept. A provider that fails, or that silently falls back to the CPU (CUDA
  libraries missing), is skipped with a one-line message. The log prints the time per tile of each candidate.
* **TensorRT** is the fastest on NVIDIA but compiles an engine for minutes on first use: only with
  `--device tensorrt` (engine cached in `models/trt_cache/`, git-ignored).
* **cv2.dnn** fallback (no onnxruntime) and `offside_code` move their networks to CUDA when OpenCV was built with it.
* **PyTorch** models (ultralytics detector / pitch keypoints, SigLIP team embeddings): `detection.device: auto`
  → `cuda:0`, else `mps`, else `cpu`; ultralytics runs in half precision on CUDA.
* **Install**: `start.command` / `start.bat` check `nvidia-smi` on every start; with an NVIDIA GPU and no CUDA
  provider they replace `onnxruntime` with `onnxruntime-gpu[cuda,cudnn]` (CUDA / cuDNN from pip, so only the NVIDIA
  driver is needed; `accel.py` calls `onnxruntime.preload_dlls()`). If that install fails the CPU build is restored.
  On a Mac nothing changes: the default wheel already has CoreML.
* **Control**: `run_analysis.py --device auto|gpu|cpu|cuda|tensorrt|directml|rocm|coreml|cv2`;
  `detection.runtime` / `detection.device` in the config. `python -m football_eval.accel` shows what a computer has
  and, for an NVIDIA GPU without the CUDA provider, the command that fixes it. The launcher prints the same at start.
* **Traceability**: `meta.json → speed` records `detector` (e.g. `onnxruntime/CUDAExecutionProvider`) and `gpu`.

Results do not change with the device: the same network and thresholds run on the GPU (fp32 for YOLOX); only the
time does. The launcher's time estimate uses the speed measured by earlier runs on the same computer, so on a GPU
computer it adapts after the first run.

## 3 · Windows compatibility

Reviewed after the GPU commit: the code ran on macOS / Linux only by accident in a few places.

| Problem on Windows | Fix |
|---|---|
| Text files read / written with the system code page (cp1252): `report.html` (⚑, →, ×) failed to save, setups with accents could be misread | every text `open()` / `read_text()` / `write_text()` (76 calls, both projects) is UTF-8; `start.bat` sets `PYTHONUTF8=1`; checked with `python -X warn_default_encoding` (0 warnings in our code) |
| Relative paths stored with `\` (setups, library listing, URLs) | always `/` (`as_posix()`), so setups move between Mac and PC |
| Uploading a video that already exists: `rename()` fails | `replace()` |
| Registry MIME types (`.js` as `text/plain`, no `.mp4`) | the launcher and the Offside studio pin their MIME types |
| Desktop shortcut: `shlex` single quotes are not `cmd.exe` quoting; skipped `start.bat`; OneDrive Desktop not found | `subprocess.list2cmdline`, `call start.bat ...`, OneDrive Desktop looked up |
| PC sleeping during a 1-2 h run (`caffeinate` is macOS only) | `SetThreadExecutionState` in `run_analysis.py` |
| Opening a folder | `os.startfile` |
| `start.bat`: no package update, `python` can be the Microsoft Store alias, LF line endings would break `goto` | update check like `start.command`, `py -3` first, `.gitattributes` (`*.bat` CRLF, `*.command` / `*.sh` LF) |
| Shortcut test assumed macOS | per platform |

Still bash-only, by design: the optional `cut_highlights.sh` / `cut_opportunities.sh` written next to the outputs
(the same clips come from `scripts/cut_opportunities.py` and the launcher on every OS).

## 4 · Package normalisation (Python 3.12-3.14, exact pins)

A new Windows PC failed with `No matching distribution found for onnxruntime`: python.org now installs Python 3.15
(released 2026-10-09) and onnxruntime (1.31, latest) publishes wheels for 3.11-3.14 only. Meanwhile the Mac ran the
system Python 3.9, so the two computers got different numpy / pandas / onnxruntime versions.

| Decision | Why |
|---|---|
| Supported Python **3.12-3.14**, 3.13 recommended (`.python-version`) | 3.15: no onnxruntime wheels yet; 3.11: dropped by numpy 2.5 and scipy 1.18; 3.13 is what the tests run on |
| **`constraints.txt`**: exact pins numpy 2.5.3, scipy 1.18.1, pandas 3.0.5, opencv-python 5.0.0.93, scikit-learn 1.9.1, matplotlib 3.11.2, PyYAML 6.0.3, onnxruntime / onnxruntime-gpu 1.29.0, jupyter 1.1.1, pytest 9.1.1 | the versions the 34 tests pass with; each has wheels for cp312-cp314 on Windows x64, macOS arm64 and Linux x64 (onnxruntime on macOS 14+) |
| Project `requirements.txt` files keep **ranges** (`numpy>=2.5,<3` ...); the root `requirements.txt` includes both plus `-c constraints.txt` | each project still installs on its own; the pins decide the exact versions; a pin outside a range fails at install (checked) |
| **`setup_env.py`** replaces the install logic of `start.command` / `start.bat` (now a few lines each) | one tested implementation instead of bash + batch; runs on any Python 3.8+ (Mac system 3.9, PC 3.15) and builds `.venv` with a supported one |
| No supported Python: explain, then offer `pymanager install 3.13` / `winget install Python.Python.3.13` / `brew install python@3.13` | the user's case: a PC with only 3.15 |
| `.venv` made with another Python is rebuilt; a `.venv` of the other OS (synced folder) is left alone and `.venv-windows` / `.venv-posix` used | the Mac's 3.9 venv must go; never destroy the other computer's environment |
| Install skipped when a stamp (requirement files, Python version, CPU/GPU runtime) is unchanged | starting the dashboard stays fast |
| onnxruntime installed apart and never fatal: `onnxruntime-gpu[cuda,cudnn]` with an NVIDIA GPU, else `onnxruntime`, never both | old macOS / unusual platforms still run (cv2.dnn), same results |
| `football_eval/envcheck.py`: Python range + installed versions vs pins; run by `setup_env.py`, printed by the launcher, `setup_env.py --check` | a hand-installed package is visible at once |
| `pip freeze` saved to `.venv/pip-freeze.txt` | compare two computers line by line |
| Optional PyTorch upgrades moved to `requirements-optional.txt` | not installed by default (heavy) |

Tests: `tests/test_environment.py` (interpreter choice incl. the 3.15-only PC, foreign venv, stamp, pins vs
requirement ranges, envcheck comparison).
